    GEMS Integration Plan¶

    This page describes how to prepare OTFP for integration into GEMS as an in-tree free-energy engine.

    The goal is not to preserve OTFP as a standalone community dependency. OTFP is stable laboratory code, while GEMS is the active experimentation environment for free-energy methods and non-NAMD potentials such as DFTB and tight-binding models. The practical integration path is to vendor the OTFP core into GEMS and drive it from GEMS, while keeping the NAMD/Tcl path as an adapter.

    Current Shape¶

    OTFP currently has four conceptual parts:

    Part Current files Role
    Core engine cfacv*.c, cvs*.c, chapeau*.c, public/internal headers Owns CVs, restraints, chapeau accumulation, solve scheduling, restart state, and force/energy calculation.
    NAMD adapter calcforces.tcl, cfacv.tcl, cvs.tcl, restraints.tcl, chapeau.tcl, data.tcl Converts NAMD TclForces data and user Tcl variables into core engine calls.
    Tcl/SWIG boundary cfacv.i, cvs.i, cfacv_tcl.h, cvs_tcl.h Exposes the selected C API to Tcl. This is an adapter boundary, not the engine model.
    Mock adapter mock.tcl, examples/test.sh, selected examples Emulates enough NAMD TclForces behavior to run fast regression tests without a full NAMD calculation.

    For GEMS, the core engine is the useful part. The Tcl/SWIG and NAMD layers are reference adapters and regression tools.

    Engine Model¶

    A molecular driver does not need to know about Tcl or NAMD. It needs a step-level OTFP engine with this lifecycle:

    1. Allocate one DataSpace.
    2. Register atom centers with masses and atom indices.
    3. Register CVs.
    4. Register restraints.
    5. Optionally register chapeau/FES state.
    6. On each step, copy current center positions into DataSpace.
    7. Compute CV values.
    8. Compute restraint forces, chapeau accumulation, target evolution, and restart/output scheduling.
    9. Read forces from DataSpace center buffers and add them to the driver.
    10. Read restraint energy and add it to the driver energy accounting.
    11. Free the DataSpace and owned objects at shutdown.

    The current public C calls that match this model are:

    Stage Current C API
    Allocate/free NewDataSpace, DataSpace_free
    Register centers DataSpace_AddAtomCenter
    Register CVs DataSpace_add_cv, set_zsd_circle, set_zsd_ring, set_d2chap, set_line, cv_access_ref, cv_access_ref2
    Register restraints DataSpace_AddRestr, restr_AddTamdOpt, restr_AddSmdOpt, restr_AddAdamOpt
    Register FES DataSpace_SetupChapeau, DataSpace_get_chapeau
    Step update DataSpace_centerPosition, DataSpace_ComputeCVs, DataSpace_RestrainingForces
    Read results DataSpace_centerForce, DataSpace_RestraintEnergy, restr_getz, restr_getu
    Restart hooks DataSpace_save_restraints, DataSpace_load_restraints, chapeau_savestate, chapeau_loadstate, chapeau_loadlambda

    This API is usable, but it still reflects the historical Tcl/NAMD workflow. New driver code should prefer the embedding facade in otfp_engine.h instead of teaching GEMS every historical function.

    Recommended GEMS Strategy¶

    Use OTFP as vendored source inside GEMS, not as an external installed dependency:

    • GEMS is the active laboratory for the methods.
    • OTFP has limited standalone maintenance pressure.
    • Keeping the code in-tree makes it easier to couple OTFP with GEMS potentials, integrators, restart formats, and future free-energy experiments.
    • The NAMD adapter can remain as an optional compatibility path or regression reference.

    Do not translate the whole OTFP codebase to Fortran before integration. The lower-risk path is:

    1. Keep the numerical core in C.
    2. Add a small C embedding facade with stable names and ownership rules.
    3. Bind that facade from Fortran using iso_c_binding.
    4. Translate or rewrite pieces later only when the integration shows a clear benefit.

    This avoids mixing language conversion, build-system migration, memory ownership changes, and scientific validation in one step.

    Embedding Facade¶

    The first driver-oriented facade lives in otfp_engine.h and otfp_engine.c. It is intentionally thin: it wraps DataSpace without changing numerical behavior. Its purpose is to give GEMS one stable dependency point while the Tcl/NAMD-facing internals continue to be refactored.

    Meson installs otfp_engine.h next to the Tcl adapter scripts under the configured include directory. Consumers should include only this header for the embedding path.

    See examples/embedding for a minimal C driver that uses this facade without Tcl, SWIG, NAMD, or the mock adapter.

    Current API:

    typedef struct otfp_engine otfp_engine;

otfp_engine *otfp_engine_create(int ncenters, int ncvs, int nrestr, long seed);
void otfp_engine_free(otfp_engine *engine);

int otfp_engine_add_center(otfp_engine *engine, int natoms,
                           const int *indices, const double *masses);
int otfp_engine_set_center_position(otfp_engine *engine, int center,
                                    const double xyz[3]);
const double *otfp_engine_center_force(otfp_engine *engine, int center);

int otfp_engine_add_cv(otfp_engine *engine, const char *type, int ncenters,
                       const int *centers, double zmin, double zmax,
                       const char *boundary, double boundary_k);
int otfp_engine_add_restraint(otfp_engine *engine, double k, double target,
                              int ncvs, const double *coefficients,
                              const char *function, double zmin, double zmax,
                              const char *boundary, double boundary_k);
int otfp_engine_add_tamd(otfp_engine *engine, int restraint,
                         double gamma, double kt, double dt,
                         int chapeau_id, int chapeau_dim);
int otfp_engine_add_smd(otfp_engine *engine, int restraint,
                        double target, int first_step, int last_step);
int otfp_engine_add_adam(otfp_engine *engine, int restraint,
                         double step_size, double beta1, double beta2,
                         double epsilon, double decay, double kt,
                         double min_step);

int otfp_engine_compute(otfp_engine *engine, int first_step, int step,
                        double external_bias);
double otfp_engine_bias_energy(otfp_engine *engine);

    Ownership and data rules:

    • otfp_engine_create allocates the engine and owned OTFP state.
    • otfp_engine_free releases all owned state and accepts NULL.
    • Center, CV, and restraint setup arrays are copied by the underlying OTFP constructors; callers do not need to keep those temporary arrays alive after setup.
    • otfp_engine_add_restraint returns the zero-based restraint index, or -1 on failure. Use that index to attach TAMD, SMD, or ADAM evolution options.
    • otfp_engine_set_center_position writes the current position for one center.
    • otfp_engine_compute computes CVs, restraint forces, chapeau updates, target evolution, and bias energy for one step.
    • otfp_engine_center_force returns a pointer to the internal force buffer for one center after otfp_engine_compute; callers must copy it before the next position update or compute call.
    • Center and CV indices are C-style zero-based indices.

    Fortran Binding Notes¶

    The first GEMS integration should use iso_c_binding against the embedding facade. The repository now includes tests/embedding_fortran.f90 as a minimal working example.

    • Store the opaque C handle as type(c_ptr).
    • Pass scalar integers as integer(c_int) or the exact width chosen by the C facade.
    • Pass coordinates and forces as contiguous real(c_double) arrays.
    • Keep allocation and destruction on the C side.
    • Convert Fortran strings to C strings only at setup time; avoid string-heavy calls in the per-step path.
    • Document index base rules explicitly. OTFP internals use C-style indices in the C API; Tcl scripts often translate from user-facing 1-based data.

    The initial Fortran layer should be thin. Its job is to map GEMS data structures into the C facade and return forces/energies to GEMS. The smoke test constructs the same two-center BOND CV and harmonic/SMD restraint as the C embedding test, computes one step, reads a force pointer with c_f_pointer, and checks that force and energy values are finite.

    Work To Do Before Asking Another Agent To Integrate¶

    1. Keep docs/architecture.md current with core/adapter boundaries.
    2. Extend the C embedding facade as GEMS needs more setup features.
    3. Expand the C embedding example toward GEMS-like repeated-step setup.
    4. Expand the Fortran iso_c_binding example toward the setup patterns GEMS will need.
    5. Expand the embedding tests beyond lifecycle/finite-value checks.
    6. Decide how OTFP will be vendored in GEMS: subtree under lib/, direct source import under a free-energy module, or a temporary development copy.
    7. Only after the C/Fortran boundary is working, evaluate whether any C modules should be rewritten in Fortran.

    What Not To Do Yet¶

    • Do not make GEMS call the SWIG/Tcl API.
    • Do not require NAMD concepts in the engine-facing API.
    • Do not translate all CV/chapeau code to Fortran before integration.
    • Do not change numerical behavior while only moving adapter boundaries.
